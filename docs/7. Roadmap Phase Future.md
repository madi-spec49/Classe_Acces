# Roadmap — Phase future (hors MVP)

Projet : Plateforme de cours à distance — association scolaire
Auteur : Madi Anli

Ce document liste les modules reportés après le MVP et les améliorations techniques prévues. Le MVP couvre : comptes créés par le staff, niveaux, cours et séances, assiduité, progression et suivi familial. Pour l'état actuel du code, le README et `db/schema.sql` font foi.

## 1. Modules fonctionnels reportés

| Module | Priorité MoSCoW | Description | Impact technique |
| --- | --- | --- | --- |
| Signalements d'absence | Should | Un parent ou un élève signale à l'avance une absence à une séance. Le staff la traite et la clôture. | Nouvelle table `absence_reports` (séance, élève, motif, statut), routes parent/élève (création) et staff (traitement), page dédiée |
| Messagerie descendante | Won't (MVP) | Le staff envoie un message (destinataire, titre, corps) aux familles. Pas de fil de discussion en temps réel. | Nouvelle table `messages`, routes staff (envoi) et utilisateur (lecture), indicateur de messages non lus |
| Paiement de la cotisation (HelloAsso) | Could | Le staff ou un élève majeur initie une demande de cotisation via l'API HelloAsso. | Intégration d'une API externe, table des paiements, gestion des retours (webhook), clés d'API en variables d'environnement |
| Notifications | Could | Le professeur est prévenu par email lorsqu'un événement le concerne (nouvel élève dans son niveau, par exemple). | Service d'envoi d'emails, file d'envoi ou tâche en arrière-plan |

## 2. Améliorations des fonctionnalités existantes

| Amélioration | Raison |
| --- | --- |
| Modification d'un cours (horaires, professeur, lien Zoom) | Aujourd'hui un cours se crée et se supprime, mais ne se modifie pas : changer un horaire oblige à le supprimer et à le recréer, ce qui efface son historique. |
| Désactivation d'un compte à la place de la suppression | Garder l'historique d'un élève parti. Le champ `is_active` existe déjà ; il faudra aussi refuser la connexion d'un compte désactivé. |
| Réaffectation des cours d'un professeur | Permettre de supprimer un professeur en transférant ses cours à un autre. |
| Changement de niveau d'un élève | Faire passer un élève au niveau supérieur sans recréer son compte. |
| Export de l'assiduité et de la progression (CSV) | Fournir un bilan de fin d'année aux familles et au bureau de l'association. |

## 3. Améliorations techniques

| Amélioration | Raison |
| --- | --- |
| Migrations avec Alembic | `Base.metadata.create_all` n'ajoute pas les colonnes manquantes sur une base existante. Alembic remplacera les scripts de `db/`. |
| Chargement automatique du fichier `.env` | Les variables doivent aujourd'hui être exportées à la main (`pydantic-settings` est déjà dans les dépendances). |
| Rafraîchissement de jeton | Éviter de reconnecter l'utilisateur toutes les 60 minutes. |
| Changement de mot de passe par l'utilisateur | Aujourd'hui seul le staff peut réinitialiser un mot de passe. |
| Contraintes `CHECK` dans les modèles SQLAlchemy | Aligner les modèles `users` et `progress_records` sur `db/schema.sql`. |
| Pipeline d'intégration continue | Lancer les tests à chaque push et chaque merge dans `develop`. |
| Déploiement | Hébergement de l'API, de la base et du front-end, avec HTTPS et une clé `JWT_SECRET_KEY` aléatoire. |

## 4. Ordre proposé

1. **Stabilisation** : migrations Alembic, `.env` automatique, modification des cours.
2. **Vie de l'association** : signalements d'absence, puis messagerie descendante.
3. **Confort** : notifications, exports, changement de mot de passe.
4. **Paiement** : intégration HelloAsso, en dernier car elle dépend d'un service externe et de la gestion de données sensibles.
