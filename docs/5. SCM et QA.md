# Classe Accès — Documentation technique (Portfolio, Stage 4)

Plateforme de cours à distance pour une association scolaire

Ce document fait partie de la documentation technique de **Classe Accès**. Le MVP s'appuie sur une stack FastAPI + SQLAlchemy + PostgreSQL + JWT, avec une interface HTML/JavaScript native.

## 6. Gestion de code source (SCM) et assurance qualité (QA)

### 6.1 Gestion de code source (SCM)

#### 6.1.1 Outil de contrôle de version

**Git** est utilisé pour le contrôle de version, avec un dépôt distant sur **GitHub** (`madi-spec49/Classe_Acces`). Le projet est réalisé seul : les rôles de chef de projet, SCM, QA et développeur sont portés par la même personne (voir `8. Plan de Sprints.md`).

#### 6.1.2 Stratégie de branchement (Git Flow simplifié)

| Branche | Rôle | Description |
| --- | --- | --- |
| `main` | Version livrée | Ne reçoit que les versions terminées, par fusion de `develop` |
| `develop` | Intégration | Regroupe les fonctionnalités terminées |
| `feature/*` | Développement | Une branche par fonctionnalité, créée depuis `develop` (`feature/auth`, `feature/create-staff-script`, `feature/update-docs`) |

**Règles appliquées :**

- Une branche `feature/*` est créée depuis `develop`.
- Le travail est commité par petites étapes.
- La branche est fusionnée dans `develop` par **pull request** sur GitHub, avec un commit de merge (pas de squash), pour garder l'historique visible.
- `develop` est fusionnée dans `main` par pull request à la fin de chaque phase. `main` ne reçoit pas de commit direct.

Le projet étant individuel, les pull requests sont fusionnées par leur auteur : il n'y a pas de revue croisée.

#### 6.1.3 Commits

Les commits sont petits et suivent la convention **Conventional Commits**, avec des messages en anglais :

| Préfixe | Usage | Exemple réel |
| --- | --- | --- |
| `feat:` | Nouvelle fonctionnalité | `feat: add script to create the first staff account` |
| `fix:` | Correction | `fix: restrict course sessions to the student's level and the course teacher` |
| `docs:` | Documentation | `docs: add future roadmap and list documents 7 and 8` |
| `refactor:` | Refactorisation | `refactor: remove public registration and enrollment requests` |
| `test:` | Tests | `test: add attendance tests` |
| `chore:` | Tâche technique | `chore: ignore local Postman sync files` |
| `revert:` | Retour en arrière | `revert: drop excused absence status` |

Les commits `revert:` documentent des décisions de périmètre : par exemple, un statut d'absence « excusée » a été ajouté puis retiré pour garder le MVP simple.

#### 6.1.4 Hygiène du dépôt

- `.env` et les secrets ne sont jamais versionnés (`.gitignore`) ; `.env.example` sert de modèle.
- Les collections Postman locales et les caches Python sont ignorés.

### 6.2 Assurance qualité (QA)

#### 6.2.1 Stratégie de test

| Niveau | Objet | Outil | État |
| --- | --- | --- | --- |
| **Tests automatisés de l'API** | Routes FastAPI avec base de test | pytest + TestClient (httpx) | **58 tests**, tous réussis |
| **Tests manuels** | Parcours dans le navigateur, un par rôle | Navigateur, Postman | Réalisés à la main, un parcours par rôle |
| Tests automatisés du front-end | — | — | Non réalisés |
| Mesure de la couverture | — | — | Non mesurée |

Les tests automatisés couvrent l'API de bout en bout (route, contrôle d'accès, base). Il n'y a pas de tests unitaires séparés d'une couche de service, car le projet n'a pas de couche de service : la logique est dans les routes.

#### 6.2.2 Outils

| Outil | Usage |
| --- | --- |
| **pytest** | Exécution des tests (`python -m pytest -v`) |
| **FastAPI TestClient** (httpx) | Appel des routes sans serveur réel |
| **SQLite en mémoire** | Base de test, créée avant chaque test et supprimée après, sans Docker |
| **Postman** | Collection locale pour tester les routes à la main |
| **`/docs` (Swagger)** | Essai manuel des routes avec un jeton |

**Limite connue** : les tests tournent sur SQLite alors que l'application utilise PostgreSQL. SQLite est plus souple sur les types et n'applique pas toujours les clés étrangères comme PostgreSQL. Les règles d'effacement en cascade sont donc vérifiées à la main sur PostgreSQL.

#### 6.2.3 Organisation des tests

Les comptes de test sont insérés directement en base par la fixture `make_user`, qui génère aussi un jeton valide. Ainsi, une panne de la route de connexion ne fait pas échouer tous les autres tests.

| Fichier | Tests | Contenu |
| --- | --- | --- |
| `test_auth.py` | 6 | Connexion réussie, mauvais mot de passe, compte désactivé refusé, `/me` avec et sans jeton, jeton invalide |
| `test_staff.py` | 8 | Création de comptes par le staff, contrôle des rôles, suppression de comptes |
| `test_courses.py` | 17 | Création et suppression de cours, horaires incohérents, filtre par niveau, séances, propriété des cours |
| `test_attendance.py` | 8 | Saisie par le professeur du cours, élève hors niveau, mise à jour d'une présence |
| `test_progress.py` | 6 | Saisie, règle de niveau, lecture limitée à l'élève, au parent lié et au staff |
| `test_parents.py` | 8 | Création de parents, liens parent-élève, parent non lié refusé, parent sans accès aux cours ni aux séances |
| `test_create_staff.py` | 5 | Script du premier compte staff : mot de passe haché, doublon, mot de passe court, email invalide |

#### 6.2.4 Scénarios d'intégration principaux

| Scénario | Déroulé | Résultat attendu |
| --- | --- | --- |
| Connexion réussie | `POST /api/auth/login` avec des identifiants valides | `200` + jeton |
| Connexion refusée | Mauvais mot de passe, ou compte désactivé | `401` |
| Accès sans jeton | `GET /api/auth/me` sans en-tête | `403` |
| Jeton invalide | `GET /api/auth/me` avec un faux jeton | `401` |
| Rôle insuffisant | Un élève appelle `POST /api/courses` | `403` |
| Horaires incohérents | `POST /api/courses` avec fin avant début | `422` |
| Niveau de l'élève | Un élève voit seulement les cours de son niveau | liste filtrée |
| Propriété du cours | Un professeur saisit l'assiduité dans le cours d'un autre | `403` |
| Élève hors niveau | Assiduité ou progression pour un élève d'un autre niveau | `400` |
| Assiduité unique | Deuxième saisie pour la même séance et le même élève | mise à jour, pas de doublon |
| Parent non lié | Un parent lit la progression d'un élève qui n'est pas son enfant | `403` |
| Parent et cours | Un parent appelle `GET /api/courses` | `403` |
| Suppression d'un professeur | Professeur qui a encore des cours | `400` |
| Compte staff protégé | Suppression d'un compte staff | `404` |

#### 6.2.5 Tests manuels

Un parcours par rôle, rejouable pour la démonstration :

1. **Staff** : créer un professeur, un élève avec son niveau, un parent, lier le parent à l'élève, créer un cours du niveau de l'élève.
2. **Professeur** : créer une séance, saisir une présence, saisir une progression.
3. **Élève** : voir uniquement les cours de son niveau, ouvrir son suivi.
4. **Parent** : voir ses enfants et leur suivi ; vérifier que `GET /api/courses` renvoie `403`.

### 6.3 Déploiement et intégration continue

| Élément | État actuel | Évolution prévue |
| --- | --- | --- |
| Environnement de développement | Poste local : `uvicorn` (API), `http.server` (front-end), PostgreSQL dans Docker Compose | — |
| Intégration continue (CI) | **Non en place** : les tests sont lancés à la main avant chaque pull request | GitHub Actions : `pytest` à chaque push et chaque pull request |
| Conteneurisation de l'API | **Non réalisée** : Docker ne lance que la base | Image Docker de l'API |
| Préproduction et production | **Non déployées** | Hébergement avec HTTPS et une clé `JWT_SECRET_KEY` aléatoire |

**Secrets** : la clé JWT et l'adresse de la base se lisent dans des variables d'environnement (`JWT_SECRET_KEY`, `DATABASE_URL`). La valeur par défaut de la clé JWT ne doit jamais être utilisée en production.
