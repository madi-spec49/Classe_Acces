# Plan de sprints — Stage 4 (MVP)

Projet : Classe Accès, plateforme de cours à distance pour une association scolaire
Auteur : Madi Anli (développeur, chef de projet, SCM et QA)
Plan rédigé le 8 octobre 2026, mis à jour le 2 novembre 2026 avec ce qui a été réellement livré
Présentation visée : semaine du 9 novembre 2026

## 1. Méthode

Cinq sprints d'une semaine, du lundi au dimanche. Le périmètre est celui des *Must Have* de la méthode MoSCoW (voir `0. User Stories et Maquettes.md`). Les *Should Have* (signalements) et les *Could Have* (HelloAsso, notifications) sont reportés, ainsi que la messagerie (voir `7. Roadmap Phase Future.md`).

Le projet est réalisé seul : la même personne est chef de projet, SCM, QA et développeur. Le plan a servi de guide, mais le développement n'a pas suivi le calendrier à la lettre : plusieurs sprints ont été avancés (voir section 2). Les dates ci-dessous viennent de l'historique Git.

## 3. Écarts avec le plan initial

| Prévu | Décision | Raison |
| --- | --- | --- |
| Demandes d'inscription à un cours, validées par le staff | Supprimées le 23 oct. | Le staff crée les comptes et chaque cours a un niveau : l'inscription n'apporte rien au MVP |
| Inscription publique (`/api/auth/register`) | Supprimée le 23 oct. | Les comptes sont créés uniquement par le staff, ce qui évite l'élévation de privilège |
| Agenda par élève et par enfant | Remplacé par les niveaux et la liste des séances d'un cours | Plus simple, et suffisant pour le besoin |
| Statut d'absence « excusée » | Ajouté puis retiré le 26 oct. (`revert`) | Trois statuts suffisent : présent, absent, en retard |
| Un parent voit les cours | Retiré le 26 oct. | Un parent n'a accès qu'au suivi de ses enfants |
| Messagerie | Hors périmètre | Reportée en phase future |
| Documentation technique mentionnant SQLite | Corrigée le 29 oct. | Le projet utilise PostgreSQL ; SQLite ne sert qu'aux tests |

## 4. Livrables du MVP

| Domaine | Livré | Preuve |
| --- | --- | --- |
| Authentification | Connexion JWT, hachage bcrypt, compte désactivé refusé | `tests/test_auth.py` (6 tests) |
| Rôles | Quatre rôles, contrôle par `require_role`, règles de propriété dans les routes | tous les fichiers de test |
| Comptes | Création et suppression par le staff, liens parent-élève, script du premier compte staff | `test_staff.py`, `test_parents.py`, `test_create_staff.py` |
| Cours et séances | Création, suppression, filtre par niveau, séances | `test_courses.py` (17 tests) |
| Assiduité | Saisie par le professeur du cours, une présence par élève et par séance | `test_attendance.py` (8 tests) |
| Progression | Saisie par le professeur, lecture par l'élève, son parent, le professeur et le staff | `test_progress.py` (6 tests) |
| Interface | Six pages HTML et JavaScript natif | tests manuels, un parcours par rôle |

Au total, 58 tests automatisés réussis.

## 5. Suivi de l'avancement

Le suivi s'est fait par les commits (convention Conventional Commits) et par les pull requests sur GitHub. Il n'y a pas de mesure de vélocité ni de suivi de bugs dans un outil dédié : les corrections apparaissent dans l'historique avec le préfixe `fix:`. Les limites connues et les améliorations prévues sont dans `7. Roadmap Phase Future.md`.
